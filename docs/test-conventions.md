# Test conventions

How tests are written, named, placed and skipped in this repository. Written 2026-10-20 (IP-01 task T01.13); the requirement behind it is BL-TV-01.

## A test states a claim

- **Each requirement maps to a named test.** The name is a snake_case sentence that says what is true, so a failure reads as a broken claim:
  `unset_optional_round_trips_as_none_not_a_default`, `layering_is_one_way`, `large_fixture_is_none_when_the_variable_is_unset`.
- **One claim per test.** If a name needs "and", it is two tests (a test that checks a rule and its synthetic violation is the exception: see Guards).
- **A test proves it can fail.** Where the claim is a rule (a guard), a companion test feeds the rule a case that breaks it and asserts it is caught.

## Where tests live

| Kind | Where |
|---|---|
| Unit tests | Inline, in a `#[cfg(test)] mod tests` at the bottom of the source file they test. |
| Integration tests | `tests/` of the crate, using only the crate's public surface. |
| Test data | **Constants, not magic paths.** The committed miniatures have named constants in `build_log_testkit::miniature` and a path helper, `miniature_path`. |

## Guards

A **guard** protects a rule that nobody should be able to break silently (layering, the MCF boundary, "an unknown version is an error"). The mandatory guard tests keep the names in section 8.2 of the library requirements, because the names are the contract. A guard works on a parsed model of what it checks, so it can be tested against a hand-made violation as well as the real thing.

The architecture guards (the layering of the crates, the Model without HDF5, Processing without IO, no MCF, the specification folder) are in `rust/build-log/tests/`: `support/` holds the guard functions over a parsed model of the workspace (read from `cargo metadata`), `architecture.rs` runs them on the real workspace, and `guards_reject_violations.rs` feeds each one a hand-made workspace that breaks its rule and checks it names the offender. **The dependencies the layers may have are data**, in `tests/data/allowed_dependencies.json` (the matrix of IP-01 Appendix C), so a new crate adds a line there and no code changes. `testdata_matches_checksums` in `rust/testkit/tests/` is the guard of the committed miniatures. `documentation_links_resolve` (`rust/build-log/tests/documentation.rs`) is the guard of the documentation: every relative link in a Markdown file of the repository must point at a file or folder that is in the repository and, if it names a heading, at one that exists, so a link to a document kept only on one machine fails it. The Model crate has its own guard, `rust/model/tests/policy_guards.rs`: a text scanner (the crate has no dependencies) that holds the types of the Common Data Model to six rules, each shown to fail on a violation made for it: every enum is `#[non_exhaustive]` or marked `// closed:`, every public struct carries a `// constructed-by:` marker and follows it, producer structs are plain, no metadata type holds bulk data, open-domain enums have an `Other(…)` variant, and no HDF5 group or path name appears in the Model.

## Three tiers of test data

1. **Committed miniatures** (`testdata/`): always available, small, redacted, with the structure of the real files. Tests may rely on them. `testdata/SHA256SUMS` lists the approved hash of each file; a miniature is committed and **never rebuilt** (HDF5 does not write the same bytes twice), and changing one needs the owner's approval.
2. **Large local fixtures** (`fixtures/`, not in git; the folder is `BUILD_LOG_FIXTURES_DIR`, default `<repo>/fixtures`): realistic-scale tests. A test that needs one asks the test kit (`large_fixture`) and **skips with a printed reason** when it is not there, never fails.
3. **The two untrimmed originals**: **no Rust code reads them.** They were used once, by the Python fixture tools, to cut the special-layer miniature and to check the trimmed copies.

## Skipping

A Rust test cannot be marked skipped, so it prints `SKIPPED: <reason>` to standard error and returns. The test kit has two macros for it, `skip_unless!(condition, "reason {}", detail)` and `large_fixture_or_skip!("extracts/v16_layer_1.h5")`. Run `cargo test -- --nocapture` to see the reasons. (The Python fixture tools mark the same idea with a `large` marker.)

## Provisional fixtures (V18)

V18 is still being finalized by its owner. A test that asserts a fact about V18 says so in its name or its first comment, and is guarded by the pinned hash of the V18 file, so that a changed V18 makes it **skip with a "re-pin required" message** instead of failing. When V18 is re-pinned, the golden outputs that depend on it are regenerated by the adapter's script and reviewed.

## Running them

```text
cargo test --workspace                                 # everything that can run here
cargo test --workspace -- --nocapture                  # and the reasons for the skips
cargo clippy --workspace --all-targets -- -D warnings
cargo fmt --all -- --check
```

**On a machine without libhdf5**, add `--features build-log/static-hdf5` to each command that builds the workspace (`test`, `clippy`, `check`, `build`): the IO layer links libhdf5, and this feature compiles it from source (the first build takes a few minutes; see the README). Where libhdf5 is installed, drop the flag. The feature-matrix test passes the flag on to the combinations that include the IO layer when it is given.

A pull request fills in [the template](../.github/pull_request_template.md): the requirement ids, the named tests, the boundaries, and the impact on provisional fixtures.

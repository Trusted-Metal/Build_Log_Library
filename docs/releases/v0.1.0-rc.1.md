# v0.1.0-rc.1: the first release candidate

The first tag of the Build Log Library that an application can pin to. It was cut by hand; later candidates will come from release automation, which is not in place yet.

## What a candidate is

- **A candidate is a tag on `main`.** Pin a tag, never a commit hash: a tag is readable in `Cargo.toml` and does not move.
- **Candidates are named `0.y.z-rc.N`.** The numbers stay below 1.0.0 until the read and write surfaces are frozen; `1.0.0` will be cut deliberately then, and it is a stability promise. Until then, a change that breaks a consumer raises the second number (0.1 to 0.2), not the first.
- **The read surface is frozen and changes only by addition.** That is `open`, `open_at` and the Model types that an opened build holds. Any other change is named in the notes of the candidate that makes it, so a pin moves deliberately and never by itself.

## What is in this candidate

- **Reading files of two versions:** V17 (what the capture software writes now, and its earlier flavours) and V16 (read-only). `build_log::supported_versions()` lists exactly what it can open; any other version is refused with an error that names the versions it can read. **There is no V18 adapter yet.**
- **One entry point, the `build-log` crate.** `open(path)` (or `open_at(group)` for a build inside a file the caller holds open) returns an `Opened`: the build as the Model's own types, the file's version, the adapter that read it, what that version can do, and a report of the three version numbers. The library chooses the adapter from the file's own version marker, so a consumer holds no code that depends on the version of a file.
- **Samples are read column by column,** with a read context that carries a cancel token, progress reporting and a budget for the cache of decoded chunks.
- **Correction grids are read whole,** as recorded; their interpretation is left to the consumer.
- **Everything is read as the file records it.** The library does not repair or reinterpret what an older writer recorded.

## What is not in it

- **No writer.** Files are read only.
- **No V18 adapter.** V18 is a draft.
- **No processing.** The processing crate is a skeleton: corrections, smoothing and spot size are still in the consumer.
- **No machine configuration.** The library never loads one and has no dependency on the library that does.

## Using it

```toml
build-log = { git = "https://github.com/Trusted-Metal/Build_Log_Library", tag = "v0.1.0-rc.1" }
```

- **To check the link,** call `build_log::library_versions()`. Its `package_version` is `0.1.0-rc.1`, and `supported_versions` lists the versions it opens.
- **To move a pin,** change `tag`, run `cargo update -p build-log`, and run the application's own tests. Cargo fetches the library over git, so the build machine needs read access to this repository.
- **Requirements:** Rust 1.85.1 or later, and libhdf5. The library builds on the HDF5 binding `hdf5-metno` 0.12; the application's own `Cargo.lock` picks the exact version, shared with the application's own use of it. On a machine without libhdf5, the `static-hdf5` feature of `build-log` compiles it from source (it needs CMake and a C compiler). The [README](../../README.md) has the build details, and [the Common Data Model](../models/cdm.md) describes the types an opened build holds.
